# 组件内核

`nd-kernel` 实现 ADR 0003 的登记、响应式依赖和停止协议。生产代码只依赖标准库；协调者由调用方放进自己的 executor，不启动线程或定时器。

## 接口

| 入口 | 行为 |
|---|---|
| `Kernel::scope`、`Key<T>::new` | 分配进程内作用域；键精确匹配类型、作用域和分区，支持 `dyn Trait` 与其他 unsized 类型 |
| `provide`、`require`、`register` | 返回 RAII 守卫；同键单一提供者，命令/订阅/槽位/定时器按类别、作用域、名字唯一 |
| `Dep::with` | 依赖不存在或调用权已撤销时返回 `None`；准入的短调用在登记表锁外执行 |
| `install(ComponentSpec, factory)` | 安装编进程序的组件定义；校验提供者冲突、依赖环与作用域，工厂等到全部依赖就绪才调用 |
| `Mount::{provide, require, register}` | 初始化登记由内核持有；依赖绑定固定到该实例启动时的提供者代次；失败或卸下时连逃逸的句柄也撤销 |
| `configure(&[ConfigChange])` | 整批校验再更新期望配置；只允许禁用 `.optional()` 组件；改变修订号表示需要重建 |
| `reconcile(now)` | 停掉失效实例及其传递消费者，再按依赖重新启动；不受影响的组件保留代次 |
| `state`、`next_deadline` | 报告等待/不可用/失败/运行/停止/禁用，以及下一次等待超时；调用方映射到 `system` 命名空间 |
| `revision`、`changed_since` | 支持多订阅者的可取消唤醒；登记、撤销或配置变化后唤醒，无需轮询 |
| `with_generation` | 在唯一协调者处提交异步结果；已停止或已换代的结果返回 `None`，不执行提交闭包 |
| `Guard::token`、`with_registration` | 命令、订阅、槽位、定时器回调按登记 token 准入；同名重新登记不会接受旧 token |
| `stop(scope, HandBack / Finish)` | 禁用目标作用域的定义，逆依赖两段停止；跨作用域消费者按 `HandBack` 收尾，仍可在依赖恢复后启动 |
| `snapshot` | 列出当前可见提供者、依赖和登记，供诊断与帧内槽位对账 |

所有身份和代次都是进程内值，不持久化、不放入 nd-wire。`register` 管理登记与调用权，不实现命令路由、时钟调度或 GPUI 实体；这些实现保存 token，在回调入口经过 `with_registration`。异步回调先携带 `Mount::generation()` 排回唯一协调者，再经 `with_generation` 提交。

`Kernel::require` 是可等待、自动看见当前提供者的外部依赖守卫；组件内部一律用 `Mount::require`，以固定本代绑定并参与换代。`Mount` 持有登记直到实例结束，调用方丢弃其返回的 `Dep` 不会卸下组件的声明依赖。

## 生命周期驱动

1. 定义全部组件；配置模块先校验整份配置的值，再把启停与需要重建的修订号交给 `configure`。依赖关系固定在 `ComponentSpec`，安装定义时校验整张图。
2. 在一次驱动开始前记录 `revision()`，然后 `reconcile(now).await`。`now` 用本进程单调时钟的经过时间。
3. 等待 `changed_since(记录的 revision)` 或 `next_deadline()` 到期，再驱动。必须在 reconcile **之前**记录 revision，防止其间的撤销被漏过。内核自身变化可能让等待立即返回一次。
4. 缺依赖从首次发现时计时；超时后 `Unavailable` 仍等待提供者恢复。初始化返回错误进入 `Failed`；相同配置修订和依赖代次不会自动重试，以免被自身登记撤销的通知唤醒后忙循环。配置修订、启停或所需提供者代次改变后重试。

工厂同步建立本地登记，不能阻塞等待外部 I/O。`Lifecycle` 的异步阶段返回标准 `Future`，可在任何支持 `Send` future 的运行时上驱动。提供者和生命周期句柄需 `Send + Sync` / `Send`；GPUI 组件通过发回 UI 线程的轻量句柄接入，不能把 GPUI App 上下文放进内核。

可原位更新的配置在提供者内部更新，不改变组件修订号。稳定收件地址作为稳定句柄传入工厂，不把短命的会话执行器登记为它的响应式依赖。

## 停止和撤销

停止开始即撤回受影响实例对新消费者的可用性以及登记回调的准入权。第一段 `quiesce` 按消费者到提供者顺序执行，保留已绑定依赖供排空、落盘、交还占用。全部第一段完成后才开始第二段 `release`，仍按消费者到提供者顺序；每个实例释放完就同步撤销它的全部登记。

驱动 future 被取消时，停止计划和已完成阶段留在 Kernel 中；下一次 `stop` 或 `reconcile` 继续。尚未完成的阶段会再次调用，生命周期实现须把进度放在自身状态里，保证重试安全。内核不把收尾超时当成功，也不越过未完成的全局屏障。

守卫 Drop 只撤销登记和后续调用权，不杀进程、不释放租约、不取消已准入的调用。低层 `provide` 守卫一旦撤销，旧依赖立即不可用；需要异步排空的提供者必须用托管组件并通过两段停止换代。直接丢弃 Kernel 只做同步撤销，需要异步收尾的进程应先显式停止各作用域。

UI 槽位撤销同步反映在 `snapshot` 和 token 准入中。外壳在当前帧结束前用 App 上下文对账、移除实体；不在守卫 Drop 里修改 GPUI。此内核保证登记失效，真实界面帧内更新由桌面外壳接入时验收。

## 验证

`tests/kernel.rs` 通过公开接口覆盖实际挂起的全局屏障、取消后续做、跨作用域停止、批次失败不部分应用、同名登记的旧 token、trait 提供者、初始化撤销和等待期限。`tests/properties.rs` 用 proptest 生成初始化失败位置、登记组合、装卸序列、依赖树换代、原位更新与逆序两段停止。

当前不涉及 CLI 依赖、CLI 存储写入、会话结构操作或派发；后续引入这些行为的模块分别维护 CLI 契约清单与引擎崩溃矩阵。
