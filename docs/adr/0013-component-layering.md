# 模块按故障隔离、状态归属、变化频率和用户能力四层切分

四份从不同角度独立写的拆分方案，经另一家模型对照十个检验场景交叉评审后合成（research/round10/COMPONENTS.md）：
- 进程按故障隔离切：守护进程、每个后端进程一个看守进程、Codex app-server、桌面界面，各在独立的 systemd 单元里，谁坏了都不连累别人。
- 守护进程里按状态归属切：每份状态只有一个写入者。跨会话的独占（后端会话租约、工作目录活动与恢复代码占用、外部写入者、Codex 线程所在运行时）由独占登记一处裁决，在会话执行器的事务里放行；租约只由观察离开：进程退出、线程卸载、`/clear` 换绑后不再持有、核实过的从未创建。
- 后端和外部依赖（CLI、Codex、Chrome、GPUI）各自关在适配器后面，每个后端进程钉住一组版本组合。会话执行器对后端只讲后端无关的动作和事实（后端端口）；退役的两套机制、转投来源与去重键、收尾判据、审批编码、就绪判据、投递对账都关在各自的适配器里。一个后端进程的输入只有一个写入者，所有写入经同一个输入序号分配。
- 代码目录、协议命名空间、界面槽位和测试夹具按用户能力命名。

每个会话一个会话执行器，对这个会话的一切改动由它唯一裁决。回退、换后端这类长操作分阶段推进，不在队列里干等回执，所以不会堵住审批和 Esc。结构操作写成操作函数，由同一个持久操作引擎落库、让出、代持、补偿和续做；守护进程重启后的恢复走平时的同一条路径。适配器把事件交给稳定的收件地址，不反向调用。

## Considered Options

- 只按一个角度切（只按功能、只按进程、只按状态、只按变化）：评审在四份里各找出走不通的场景，比如只按功能切时会话级编排没有归属、只按进程切时退役状态存了两份。
- 适配器只做编解码，后端细节由会话层按后端分支（第 10 轮初稿的 Extras 旁路）：退役、转投、审批编码散到约七处，ADR 0009 的后端无关落空。
- 独占登记用独立事务，再加发件前的第二道准入：每次写后端会话多两次提交，检查散到每条传输路径上。
